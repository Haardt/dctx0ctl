# dctx0 delivery

Optimize time to usable, fully accepted behavior within the user's scope. Early
working results and complete final acceptance are both required. Test counts,
coverage and historical PASS totals do not measure product completion. Follow
project instructions and existing authorization; this skill does not authorize
subagents, deployments or production resource access.

## Plan from actual requirements and production

Inspect the installed CLI and relevant command help. Inventory every active task
in the agreed scope using filtered lists or [queries](references/query.md), then
read every task's complete requirements, prerequisites, existing results and
selected profiles through pinned packages or required context pages. Shared
content needs reading once while retained. Missing mandatory context blocks
implementation of that requirement; do not silently omit it.

Use dctx0's prerequisite DAG, ownership and blocker reports. Inspect the actual
production entry point and composition before allocating implementation, adapter
or coverage work. Distinguish existing components, connected production behavior
and fixture-only wiring. Group task IDs into cohesive deliverables with a real
user action, entry point, observable result and full acceptance obligations.
The first deliverable should establish a complete representative production path.
Keep remaining platforms, security guarantees and other requirements in scope.

Keep task definitions immutable. Delivery grouping is an implementation view over
existing IDs, not a new task database or invented dependency graph. Export
`tasks package` for prerequisite-closed anchors; use multiple packages when a
functional deliverable has multiple anchors. Save their plan/event pins and
source identities. Check completeness, boundary results, ownership and blockers;
a package read grants no reservation. Use guarded claims and transitions when
execution is authorized. Use the installed implementation skill for adapter and
evidence mechanics, if available; otherwise inspect the CLI and project guide.

## Deliver and validate at useful boundaries

Connect one real production path and execute a representative native check early.
Bring forward infrastructure only when it blocks that outcome or its necessary
proof. Deliver production wiring, focused tests and testing-only adapters together.
Finish the current deliverable before starting unrelated helper work; on a
necessary switch retain the exact blocker and unfinished work in the existing
package handoff. Do not create a management record per task or chat turn.

During implementation use focused regressions and actual counterexample replay.
Run broad coverage, bundled native acceptance and required project gates at the
functional package boundary, or earlier where project rules require them. Repeat
successful checks when relevant inputs change or an unresolved concern warrants
it; record that reason. A status request or context reset alone is not a reason.
Batching never reduces mandatory scope, cases, budgets, coverage or reviews.

Use existing change intelligence before rediscovering context or rerunning work:

- `tasks package-delta` and `package-apply` update requirements, profiles, state,
  prerequisite results and evidence. Retain the reconstructed full package and
  reload changed required context. Package deltas do not check application freshness.
- `verify review-changes` identifies changed source inventory and affected review
  duties. Inspect actual code impact; a changed file does not identify one duty
  automatically or renew approval. Spec diff/impact describes specification changes.
- Compact `verify show`, `verify compare` and replay locate failures and repairs.
  `verify adoption-preview` explains current delivery blockers without publishing.
- If available and applicable, experimental coverage `affected` suggests Rust
  project tests from historical coverage. Unknowns remain explicit and
  `can_skip_other_tests: false` grants no permission to omit other required tests.

A change report is not fresh execution evidence. Respect source/configuration,
requirement, dependency and runtime bindings; do not invent cached PASS reuse.
At package closure reconcile fulfilled IDs through guarded delivery commands.
Done and testing PASS remain separate. Assigned source-bound Review tasks may be
Done/Unverified when approved under their actual rules. Preserve FAIL, UNKNOWN,
missing evidence and incomplete final acceptance explicitly.

## Steer by observable outcomes

At agreed checkpoints report what the user can now start, the missing production
features, newly delivered behavior and check results with source/run identities.
If consecutive checkpoints produce only diagnostics or metrics, inspect the
critical path and make a concrete prioritization change. Do not invent a fixed
checkpoint frequency or delegate unless authorized.

Read [delivery measures and learning](references/delivery-measures.md) when
planning a substantial run. Establish its starting pins, KPI definitions and
available measurements. Maintain `DCTX0_IMPROVEMENT_WORKFLOW.md` in the application
root when concrete workflow friction is found, preserving existing content and
local rules. Record actionable observations and evaluate changes; do not turn
unproven alpha workarounds into universal instructions or weaken acceptance.
